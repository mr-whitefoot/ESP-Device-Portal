# 0012. Обновление с GitHub выполняет страница портала, а не устройство

Статус: принято.

## Контекст

Обновление требовало компьютера со собранным репозиторием: espota из
PlatformIO или ручная отдача bin-файла на странице Firmware upgrade. Владелец
устройства должен был сам знать, что вышла новая версия.

Естественное решение — устройство само ходит к GitHub за свежим релизом.
Стоимость измерена: GitHub отдаёт всё только по HTTPS, а HTTPS на ESP8266 —
это BearSSL, 50–70 КБ флеша и около 25 КБ кучи на handshake, потому что
MFLN у CDN GitHub нет и буферы обмена не урезать. Запас под OTA на версии
4.2.0:

| Образ | Свободно до предела OTA |
|---|---|
| `esp01_relay` | 7 472 |
| `esp01_ds18b20` | 9 552 |
| `esp07s_relay8` | 5 552 |
| `d1_mini_*` | около 570 000 |

Для трёх из пяти образов не хватает на порядок. Сжатие образа (gzip-OTA)
поднимает потолок однометровых плат примерно на 85 КБ — этого хватило бы на
флеш, но не на кучу, и выигрыш достаётся только пути espota; разбор в
`HANDOFF.md`.

Отдельно выяснилось, что образы из ассетов релиза браузеру недоступны:
`release-assets.githubusercontent.com` отдаёт файл без заголовка
`Access-Control-Allow-Origin`. У `api.github.com`, `raw.githubusercontent.com`
и GitHub Pages CORS открыт.

## Решение

В интернет ходит не устройство, а страница, которую оно отдало. Снаружи
сценарий тот же: человек открывает портал, видит «новая версия доступна» и
нажимает кнопку.

Зеркалом служит GitHub Pages: релизный workflow кладёт туда те же бинарники и
`manifest.json` с версией, именем файла, размером и md5 каждого образа. Ключ в
манифесте — `custom_device_name`, а прошивка знает своё имя из `-D IMAGE_NAME`,
которое приходит из той же опции, что и имя bin-файла.

Скрипт отдаётся отдельным маршрутом `/fw.js`, а не вставляется в страницы: он
нужен двум страницам, а во флеше должен лежать один раз. Устройство добавляет
к странице только свои факты — версию, имя образа и свободное место под новый
образ. Сравнение версий числовое и живёт в скрипте: в прошивке оно стоило бы
флеша, а никакой другой её части не нужно.

Браузер скачивает `.bin` с зеркала и отправляет его на существующий
`/ota_update` — тем же multipart-запросом, которым работает ручная заливка.

Заливается несжатый образ, хотя устройство приняло бы и `.bin.gz`. Обработчик
GyverPortal объявляет `Update.begin()` весь свободный флеш, из-за чего область
стейджинга встаёт сразу за текущим скетчем, а eboot распаковывает от нуля вверх
без проверки перекрытия. Сжатый образ, который в распакованном виде больше
оставшегося промежутка, затёр бы собственный источник — это кирпич, лечится
только UART.

Перед скачиванием скрипт сверяет размер образа со свободным местом, посчитанным
той же формулой, которой воспользуется обработчик загрузки. Иначе отказ
`UPDATE_ERROR_SPACE` приходил бы после того, как полмегабайта уехало по воздуху.

## Последствия

Цена — 2 144–2 176 байт образа, почти целиком текст скрипта. У `esp07s_relay8`
после этого остаётся 3 376 байт запаса, то есть решение потратило больше
трети того, что было.

Обновление работает на всех пяти образах одинаково, включая ESP-01, и не
требует ни компьютера с репозиторием, ни знания адреса устройства сверх того,
что человек уже открыл его портал.

Интернет нужен браузеру, а не устройству. При подключении к точке доступа
самого устройства проверка честно скажет `GitHub unreachable`.

Подлинность образа держится на HTTPS до зеркала. Проверить md5 или подпись в
браузере нельзя: портал работает по http, а `crypto.subtle` доступен только в
защищённом контексте. Участок «браузер — устройство» проходит по локальной
сети и не защищён и сейчас, при ручной заливке.

Зеркало требует одной ручной настройки репозитория: Settings → Pages → Source
= GitHub Actions. Шаги публикации стоят в workflow после создания релиза,
поэтому невключённый Pages ломает зеркало, а не выпуск прошивок.

По мере роста образа свободного места остаётся меньше, и однажды проверка
размера начнёт отказывать в установке через портал раньше, чем это заметит
сборка. Это тот же предел, что уже сторожит `custom_ota_max_size`, просто
увиденный с другой стороны.
