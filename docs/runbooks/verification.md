# Проверка изменений

Этот runbook применяется перед прошивкой железа и выпуском версии. Правила,
какие устройства разрешено прошивать, находятся в корневом `AGENTS.md`.

## 1. Статические проверки

```bash
git diff --check
pio test -e native
```

Native-набор покрывает настройки, автоматы Wi-Fi/MQTT/NTP, таймеры, реле,
топики, разбор команд, кнопку на корпусе, светодиод состояния, разбор
десятичных чисел и медианный фильтр. Он не заменяет проверку GyverPortal,
реального радио, MQTT-транспорта и файловой системы.

## 2. Сборка образов

При изменении общего ядра собрать все конечные прошивки:

```bash
pio run -e esp01_relay
pio run -e d1_mini_relay
pio run -e esp07s_relay8
pio run -e sonoff_basic_relay
pio run -e esp01_ds18b20
pio run -e d1_mini_ds18b20
```

Для каждого образа проверить в начале вывода сборки плату:

- `esp01_relay`: `Espressif Generic ESP8266 ESP-01 1M`;
- `d1_mini_relay`: `WeMos D1 R2 and mini` и 4 MB Flash;
- `esp07s_relay8`: `Espressif Generic ESP8266 ESP-07S`; профиль принудительно
  использует фактические 1 MB Flash и разметку `eagle.flash.1m64.ld`.
- `sonoff_basic_relay`: `Sonoff Basic`; профиль подменяет предложенную
  манифестом разметку на `eagle.flash.1m64.ld`, поэтому доступный объём
  программы такой же, как у ESP-01 — 958448 байт. Заголовок BIN проверять тем
  же `xxd -l 4`: здесь ESP8285, и байт режима флеша обязан быть `03` (dout),
  иначе устройство замрёт на `rf cal sector` после заливки по UART.
- `esp01_ds18b20`: `Espressif Generic ESP8266 ESP-01 1M` и OneWire на GPIO2;
- `d1_mini_ds18b20`: `WeMos D1 R2 and mini`, 4 MB Flash и OneWire на
  D2/GPIO4.

Манифест `esp07s` в PlatformIO всё равно печатает строку `HARDWARE: ... 4MB
Flash`; она не учитывает переопределённый linker script. Для этой платы
проверять нужно доступный объём программы 958448 байт, строку `OTA headroom`
с пределом 479232 и заголовок BIN. Команда
`xxd -l 4 .pio/build/esp07s_relay8/ESP_Relay_ESP07S_8ch_v<version>.bin`
должна закончиться байтом `20`: старший полубайт `2` кодирует 1 МБ Flash в
формате образа ESP8266.

При изменении только устройства всё равно убедиться, что его окружение
собирается. В конце реального создания BIN должна появиться строка вида:

```text
OTA headroom: <размер> of <предел> bytes used (<доля>%), <запас> left
```

Обычный отчёт `Flash` может использовать другой предел и не подтверждает
возможность следующего OTA. Проверка привязана к фактическому `.bin` post-action-скриптом,
а предел берётся из профиля платы: 479232 байта для ESP-01/ESP-07S и 1044464
байта для D1 mini.
Если машинный код не изменился, SCons может не пересоздавать BIN и не печатать
строку — это нормально. Если новая прошивка ожидалась, перед загрузкой нужно
увидеть и создание BIN, и `OTA headroom`.

## 3. Диагностика длительности `loop()`

Для поиска блокирующей подсистемы собрать диагностическое реле:

```bash
pio run -e esp01_relay_metrics -t upload
```

Окружение добавляет `LOOP_METRICS`; обычные образы метрики не содержат. Худший
проход печатается раз в секунду с разбивкой по OTA, settings, MQTT, publish,
portal, Wi-Fi, NTP и device.

Лог можно читать без serial:

```bash
curl -s http://<ip>/log > /dev/null
curl -s 'http://<ip>/GP_update?log='
```

Чтение `GPlog` очищает его, поэтому каждый ответ — единственная копия
накопленных строк. Имя параметра именно `log`, как у `GP.AREA_LOG(glog, 20)`;
`GP_log` относится к внутреннему логу GyverPortal и здесь бесполезен.

После диагностики вернуть на устройство обычный образ.

## 3a. Проверка лога

Строки идут одновременно в serial и в портал и выглядят так:

```text
[    2.117] I wifi connected ip=192.168.1.50 rssi=-61
```

Смотреть на загрузке:

- баннер называет модель, версию, дату сборки, chip ID, свободную кучу и
  `reset=` — причина сброса живёт только до следующей перезагрузки;
- подключение к Wi-Fi печатает адрес независимо от того, поднималась ли точка
  доступа;
- `ntp synced time=` появляется после первой синхронизации; по этой строке
  аптайм остальных строк переводится в календарное время;
- каждая перезагрузка объясняет свою причину строкой `reboot requested
  reason=`.

Отладочные строки (адреса топиков, периодические публикации) собираются
флагом `-D LOG_LEVEL=4`; обычный образ их не содержит. Проверять, что в логе
нет паролей: у них печатается только `new`/`kept`.

## 3b. Проверка обновления с GitHub

Проверять после любой правки страниц портала или релизного workflow.

Скрипт страницы с 4.7.0 лежит на зеркале, и его поведение закрыто стендом —
он гоняется без железа и без браузера, поэтому идёт первым:

```bash
node test/web/fw_test.js
```

Дальше серверная часть, тоже без браузера:

```bash
M=https://mr-whitefoot.github.io/ESP-Device-Portal
curl -s -D- $M/fw.js -o /dev/null | grep -i 'HTTP/\|access-control\|content-type'
curl -s $M/manifest.json | python3 -m json.tool | head -20
curl -s http://<ip>/ | grep -o "FW={[^}]*}"
curl -s http://<ip>/ | grep -o "script src='[^']*'"
```

Тег `script` на странице устройства обязан указывать на зеркало: с 4.7.0
скрипт не отдаётся с устройства, и маршрута `/fw.js` больше нет.

У `fw.js` на зеркале обязаны быть `200`, `Access-Control-Allow-Origin: *` и
`content-type` javascript: без CORS браузер не выполнит его на странице
устройства. В манифесте проверить, что `history` перечисляет пять версий,
свежая первой, у каждой непустые `notes` и свой набор образов (с 4.8.1 их
шесть), а
верхние `version`/`images` совпадают с первой записью `history` — на них живут
прошивки 4.3.1–4.6.0, которые про историю не знают.

В фактах должны стоять текущая версия, имя своего образа (`Relay`,
`Relay_D1_mini`, `Relay_ESP07S_8ch`, `Relay_Sonoff_Basic`, `DS18B20`,
`DS18B20_D1_mini`), свободное
место `f` и конец области скетчей `e`. Проверить арифметикой: для 1 МБ плат
`e` равно 962560, а `f` — это `e` минус текущий скетч, округлённый вверх до
4 КБ. Разошлось — значит на устройстве не та прошивка, которую собирали.

Приём образа — свой код на пути прошивки, поэтому проверяется матрицей, а не
одной удачной заливкой. Все восемь строк выполняются на реле, то есть на
однометровой плате: именно там границы стейджинга что-то значат. После каждой
неудачной устройство обязано остаться на прежней прошивке и ответить сразу.

```bash
B=.pio/build/esp01_relay/ESP_Relay_v<version>.bin
S=$(stat -f%z $B); M=$(md5 -q $B)
Z=$B.gz; ZS=$(stat -f%z $Z); ZM=$(md5 -q $Z)

curl -s http://<ip>/ota_update | grep -o "Update from GitHub\|Upload file"   # страница
curl -F "firmware=@$B" "http://<ip>/ota_update"                             # ручная заливка
curl -F "firmware=@$B" "http://<ip>/ota_update?size=$S&md5=$M"              # путь скрипта, .bin
curl -F "firmware=@$Z" "http://<ip>/ota_update?size=$ZS&md5=$ZM"            # путь скрипта, .gz
curl -F "firmware=@$Z" "http://<ip>/ota_update"                             # .gz без размера
curl -F "firmware=@$B" "http://<ip>/ota_update?size=$S&md5=00000000000000000000000000000000"
curl -F "firmware=@$B" "http://<ip>/ota_update?size=100000"
curl -F "dummy=1"      "http://<ip>/ota_update"
```

Ожидаемые ответы: `Update success` у первых трёх заливок, затем `gz needs size`,
`MD5 verification failed`, `Not Enough Space` и `no firmware file in request`.
Заливка несжатого образа около 477 КБ занимает примерно 15 секунд, сжатого
около 330 КБ — примерно 10; после успешной устройство перезагружается само
через секунду.

Заливку `.gz` проверять обязательно и обязательно на однометровой плате: она
единственная, где ошибка в объявленном размере приводит не к отказу, а к тому,
что eboot затирает собственный источник, — устройство после этого поднимается
только через UART. Отдельно убедиться, что после успешной установки сжатого
образа версия в `Information` сменилась, а `flash=` в загрузочном баннере
остался прежним: для `.gz` `Updater` байты режима не патчит.

Строка `.gz` без размера — вторая половина той же проверки. Отказ обязан
случиться до `Update.begin()`, то есть мгновенно и без записи во флеш.

Пустой POST без файла проверять обязательно: обработчик загрузки в этом случае
не зовут ни разу, и ошибка в учёте состояния превращает такой запрос в
«успешное обновление» с перезагрузкой.

В браузере проверить обе страницы: главная показывает строку (ссылку на страницу обновления) только когда
релиз новее, страница Firmware upgrade отвечает всегда. На ней же:

- выбор версии заполнен пятью релизами, своя помечена `(installed)`;
- переключение версии меняет текст «что нового» под ним;
- кнопка `Install` доступна и тогда, когда стоит уже свежая версия;
- откат: выбрать прошлую версию, поставить её и убедиться, что `Information`
  показывает именно её. На однометровой плате это заодно проверка первой
  границы — в несжатой форме манифеста откат идёт впритык.

Проверка идёт к зеркалу на GitHub Pages, поэтому в сети без интернета и при
подключении к точке доступа самого устройства скрипт не загрузится вовсе и
ожидается `Offline` — не `GitHub unreachable`: эту строку пишет уже сам
скрипт, когда он есть, а зеркало недоступно.

## 4. Проверка MQTT

Создать локальную конфигурацию из примера и запустить наблюдатель:

```bash
cp tools/broker.ini.example tools/broker.ini
python3 tools/mqtt_watch.py 'homeassistant/switch/ESP_Relay/#' 30
```

`ESP_Relay` — имя устройства по умолчанию; если оно изменено, подставьте своё.

Скрипт показывает topic, payload и флаг retain. Сообщение, полученное сразу
после подписки из хранилища брокера, имеет `retain=1`; живая публикация того же
retained-сообщения приходит подписчику с `retain=0` согласно MQTT.

Проверить:

- после подключения присутствуют retained `config`, `state`, `available`;
- команда доходит до устройства, состояние публикуется сразу;
- при недоступном брокере портал продолжает отвечать;
- после возврата брокера клиент переподключается без перезагрузки устройства.

Для смены `Topic prefix` запустить наблюдатель на прежнем корне, сменить
префикс в форме MQTT и дождаться подключения плюс 30 секунд отложенной уборки.
Под прежним корнем должны прийти пустые retained `config`, `state` и
`available`, повторный запуск наблюдателя на нём ничего не получает, а под
новым корнем сущность объявлена заново. Сохранение формы с тем же префиксом
ничего не снимает. Смена префикса при выключенном брокере снимает старые
топики после его возвращения, в том числе через перезагрузку.

Для factory reset сначала запустить наблюдатель на прежнем корне топиков, затем
подтвердить сброс в портале. После перезагрузки повторный запуск наблюдателя не
должен получить ни одного retained `config`, `state` или `available` прежней
сущности. В живом потоке перед перезагрузкой ожидаются пустые retained payload;
`offline` после них появляться не должен. Обычная кнопка Reboot, напротив,
обязана оставить retained `available=offline`.

## 5. Smoke-тест реле

Перед прошивкой сверить образ и пин:

| Плата | Окружение | Файл | Пин реле |
|---|---|---|---|
| ESP-01 | `esp01_relay` | `ESP_Relay_v<version>.bin` | GPIO0 |
| D1 mini | `d1_mini_relay` | `ESP_Relay_D1_mini_v<version>.bin` | D1 (GPIO5) |
| ESP-07S, 8 каналов | `esp07s_relay8` | `ESP_Relay_ESP07S_8ch_v<version>.bin` | 16,14,12,13,15,0,4,5 |
| Sonoff Basic R2 | `sonoff_basic_relay` | `ESP_Relay_Sonoff_Basic_v<version>.bin` | GPIO12 (кнопка GPIO0, светодиод GPIO13) |

Реле можно прошивать без дополнительного согласования. Если в одну проверку входят
реле и DS18B20, первым прошивается реле; датчик не входит в этот smoke-тест.

- Портал открывается, версия и индикатор Wi-Fi отображаются.
- Команды портала и MQTT меняют состояние и сразу публикуют его.
- Инверсия не создаёт промежуточного импульса при загрузке.
- В `Button mode` команда `ON` даёт импульс около 500 мс, `OFF` отпускает
  раньше, а таймеры не показывают `Action` и выполняют только `On`.
- В `Button mode` на главной вместо переключателя стоит кнопка `Push`, и
  каждое нажатие даёт импульс.
- При выключенном `Button mode` таймеры снова показывают сохранённые действия.
- Если менялись формы, сохранить их без изменения значений и убедиться, что
  HTTP-ответ приходит до применения Wi-Fi или перезагрузки.
- На D1 mini отдельно проверить, что управляется именно D1/GPIO5, а соседние
  D2/GPIO4 и D4/GPIO2 не меняют уровень. Реле и датчик собираются разными
  образами, поэтому D2 у датчика релейному образу не мешает.

На Sonoff Basic R2 дополнительно, до того как корпус закрыт:

- Светодиод тёмный на всей загрузке, если реле поднимается выключенным.
  Смотреть именно момент подачи питания: он горит от низкого уровня, и
  ошибка порядка `digitalWrite`/`pinMode` даёт вспышку на всю загрузку.
- Короткое нажатие переключает реле, состояние сразу уходит в MQTT и в
  портал, а светодиод повторяет выход. Дребезг не даёт двойных срабатываний.
- В `Button mode` нажатие даёт тот же импульс около 500 мс.
- Кнопка, зажатая при подаче питания, ничего не переключает и ничего не
  сбрасывает: это обычный заход в режим прошивки.
- Удержание около 7 секунд запускает частое мигание, отпускание до 10 секунд
  возвращает светодиод к состоянию реле и настройки остаются на месте.
- Удержание 10 секунд сбрасывает настройки: в логе `button hold: factory
  reset`, retained-топики сняты с брокера, устройство поднимается точкой
  доступа. Проверять на устройстве, которое не жалко перенастроить.

Для восьмиканальной платы до подключения нагрузки:

- сверить фактическую маркировку модуля ESP-07S и распиновку платы;
- проверить внешние уровни GPIO0 и GPIO15: это загрузочные GPIO, неверная
  подтяжка не исправляется прошивкой;
- выполнить несколько холодных стартов и убедиться, что все каналы остаются
  выключенными до завершения загрузки;
- по очереди переключить каналы 1–8 из портала и убедиться, что срабатывает
  только соответствующий GPIO;
- проверить восемь retained discovery по стабильным `relay_1` ... `relay_8`,
  один общий state JSON, общий availability и восемь command topic;
- переименовать канал и убедиться, что его topic и `uniq_id` не изменились;
- проверить индивидуально invert, Button mode и восстановление состояния;
- для каждого из пяти таймеров проверить выбор целевого канала; у канала в
  Button mode любое действие таймера должно давать только импульс `On`;
- выбрать у таймера `All relays` и по очереди проверить `On`, `Off` и `Toggle`:
  все восемь обычных каналов должны изменить состояние в одном проходе;
- повторить `All relays` со смешанными режимами: обычные каналы выполняют
  выбранное действие, каналы в Button mode дают импульс `On`.

## 5a. Автоматический прогон на реле

Сетевую часть раздела 5 и раздела 4 выполняет `tools/hw_test.py`: только
стандартная библиотека, MQTT тем же клиентом, что в `tools/mqtt_watch.py`.
Адрес устройства задаётся явно и в репозитории не хранится:

```bash
python3 tools/hw_test.py --list
python3 tools/hw_test.py --host <адрес>
python3 tools/hw_test.py --host <адрес> --only timer --only reboot
python3 tools/hw_test.py --host <адрес> --ota-image <файл .bin или .bin.gz> --expect-version X.Y.Z
python3 tools/hw_test.py --host <адрес> --destructive    # ещё и смена Topic prefix
python3 tools/hw_test.py --self-test                     # чистые помощники, без устройства
```

Брокер берётся из `tools/broker.ini` (или `--broker-ini PATH`); без файла
проверки MQTT выводятся как `SKIP`. Авторизация портала -- `--user` и
`--password` либо `HW_TEST_USER` и `HW_TEST_PASSWORD`. Код выхода ненулевой при
любом `FAIL`. Образ датчика и всё, кроме одноканального `Relay`, тест отвергает.

Перед началом снимаются состояние реле и формы Preferences, Timers и MQTT;
каждая проверка откатывает своё, в конце всё сверяется со снимком и печатается
`Итог состояния`. Factory reset, Wi-Fi и префикс топиков (без `--destructive`)
не затрагиваются. Реле во время прогона щёлкает, нагрузку лучше отключить.

Покрыто: страницы портала и разбор `FW`; переключатель портала и лог;
инверсия; суточный таймер; сохранение настройки через перезагрузку; `Save relay
status` в обе стороны; retained discovery, availability и state; команды MQTT
(в том числе нераспознанная); `Button mode`; кнопка Reboot с `offline` ->
`online`; с `--destructive` смена и возврат префикса с уборкой старого корня;
с `--ota-image` отказ при неверном md5 и заливка образа (`Update success`,
перезагрузка, `FW.f` до и после). Если образ совпадает с работающим, `FW.f` не
меняется, и доказательством служит перезагрузка с возвратом портала.

Остаётся вручную: физическая кнопка и светодиод, точка доступа и captive
portal, восстановление Wi-Fi (раздел 7), factory reset, уровни на пинах и
отсутствие щелчка при загрузке, D1 mini и многоканальная плата, а также
поведение Home Assistant.

Самотесты `tools/hw_test.py` и `tools/fleet_update.py` гоняет CI (задача
`tools`).

## 6. Smoke-тест DS18B20

| Плата | Окружение | Файл | OneWire |
|---|---|---|---|
| ESP-01 | `esp01_ds18b20` | `ESP_DS18B20_v<version>.bin` | GPIO2 |
| D1 mini | `d1_mini_ds18b20` | `ESP_DS18B20_D1_mini_v<version>.bin` | D2 (GPIO4) |

- Home Assistant создаёт sensor с единицами и классом measurement.
- Пока валидного чтения нет, состояние `unknown`, а не `0 °C`.
- Отключённый датчик не публикует `-127 °C` и не забивает лог повторами.
- После возврата датчика чтение возобновляется без перезагрузки.
- Изменение периода опроса применяется после сохранения Preferences.
- Портал и captive portal остаются отзывчивыми во время преобразования.

## 7. Проверка восстановления Wi-Fi

- Короткий разрыв не меняет режим до истечения защитной выдержки.
- После длительного разрыва устройство сначала повторяет STA-подключение.
- После неудачи поднимается AP с captive portal.
- Новые credentials применяются после успешного ответа формы.
- При возврате роутера устройство само подключается; AP закрывается только
  когда к нему больше нет клиентов.
