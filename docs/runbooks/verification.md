# Проверка изменений

Этот runbook применяется перед прошивкой железа и выпуском версии. Правила,
какие устройства разрешено прошивать, находятся в корневом `AGENTS.md`.

## 1. Статические проверки

```bash
git diff --check
pio test -e native
```

Native-набор покрывает настройки, автоматы Wi-Fi/MQTT/NTP, таймеры, реле,
топики, разбор команд и медианный фильтр. Он не заменяет проверку GyverPortal,
реального радио, MQTT-транспорта и файловой системы.

## 2. Сборка образов

При изменении общего ядра собрать обе конечные прошивки:

```bash
pio run -e esp01_relay
pio run -e esp01_ds18b20
```

При изменении только устройства всё равно убедиться, что его окружение
собирается. В конце реального создания BIN должна появиться строка вида:

```text
OTA headroom: 471872 of 481280 bytes used (98.0%), 9408 left
```

Обычный отчёт `Flash` использует другой предел и не подтверждает возможность
следующего OTA. Проверка привязана к фактическому `.bin` post-action-скриптом.
Если машинный код не изменился, SCons может не пересоздавать BIN и не печатать
строку — это нормально. Если новая прошивка ожидалась, перед загрузкой нужно
увидеть и создание BIN, и `OTA headroom`.

## 3. Диагностика длительности `loop()`

Для поиска блокирующей подсистемы собрать диагностическое реле:

```bash
pio run -e esp01_relay_metrics -t upload
```

Окружение добавляет `LOOP_METRICS`; обычные образы метрики не содержат. Худший
проход печатается раз в секунду с разбивкой по OTA, settings, MQTT, publish,
portal, Wi-Fi, NTP и device.

Лог можно читать без serial:

```bash
curl -s http://<ip>/log > /dev/null
curl -s 'http://<ip>/GP_update?log='
```

Чтение `GPlog` очищает его, поэтому каждый ответ — единственная копия
накопленных строк. Имя параметра именно `log`, как у `GP.AREA_LOG(glog, 20)`;
`GP_log` относится к внутреннему логу GyverPortal и здесь бесполезен.

После диагностики вернуть на устройство обычный образ.

## 3a. Проверка лога

Строки идут одновременно в serial и в портал и выглядят так:

```text
[    2.117] I wifi connected ip=10.0.1.22 rssi=-61
```

Смотреть на загрузке:

- баннер называет модель, версию, дату сборки, chip ID, свободную кучу и
  `reset=` — причина сброса живёт только до следующей перезагрузки;
- подключение к Wi-Fi печатает адрес независимо от того, поднималась ли точка
  доступа;
- `ntp synced time=` появляется после первой синхронизации; по этой строке
  аптайм остальных строк переводится в календарное время;
- каждая перезагрузка объясняет свою причину строкой `reboot requested
  reason=`.

Отладочные строки (адреса топиков, периодические публикации) собираются
флагом `-D LOG_LEVEL=4`; обычный образ их не содержит. Проверять, что в логе
нет паролей: у них печатается только `new`/`kept`.

## 4. Проверка MQTT

Создать локальную конфигурацию из примера и запустить наблюдатель:

```bash
cp tools/broker.ini.example tools/broker.ini
python3 tools/mqtt_watch.py 'homeassistant/switch/ESP_Relay/#' 30
```

Скрипт показывает topic, payload и флаг retain. Сообщение, полученное сразу
после подписки из хранилища брокера, имеет `retain=1`; живая публикация того же
retained-сообщения приходит подписчику с `retain=0` согласно MQTT.

Проверить:

- после подключения присутствуют retained `config`, `state`, `available`;
- команда доходит до устройства, состояние публикуется сразу;
- при недоступном брокере портал продолжает отвечать;
- после возврата брокера клиент переподключается без перезагрузки устройства.

## 5. Smoke-тест реле

- Портал открывается, версия и индикатор Wi-Fi отображаются.
- Команды портала и MQTT меняют состояние и сразу публикуют его.
- Инверсия не создаёт промежуточного импульса при загрузке.
- В `Button mode` команда `ON` даёт импульс около 500 мс, `OFF` отпускает
  раньше, а таймеры не показывают `Action` и выполняют только `On`.
- При выключенном `Button mode` таймеры снова показывают сохранённые действия.
- Если менялись формы, сохранить их без изменения значений и убедиться, что
  HTTP-ответ приходит до применения Wi-Fi или перезагрузки.

## 6. Smoke-тест DS18B20

- Home Assistant создаёт sensor с единицами и классом measurement.
- Пока валидного чтения нет, состояние `unknown`, а не `0 °C`.
- Отключённый датчик не публикует `-127 °C` и не забивает лог повторами.
- После возврата датчика чтение возобновляется без перезагрузки.
- Изменение периода опроса применяется после сохранения Preferences.
- Портал и captive portal остаются отзывчивыми во время преобразования.

## 7. Проверка восстановления Wi-Fi

- Короткий разрыв не меняет режим до истечения защитной выдержки.
- После длительного разрыва устройство сначала повторяет STA-подключение.
- После неудачи поднимается AP с captive portal.
- Новые credentials применяются после успешного ответа формы.
- При возврате роутера устройство само подключается; AP закрывается только
  когда к нему больше нет клиентов.
